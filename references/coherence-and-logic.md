# 逻辑与连贯诊断指南

本文件面向长文润色、多段重构，或出现“短句堆砌、单句都懂但连读费力、前后跳脱”的文本。普通短回答不必加载本文件。

诊断按五层自小到大排查：词句清晰度 -> 易读与句式节奏 -> 前后句逻辑 -> 前后段逻辑 -> 上下文一致性。修改时始终遵守核心规则：保留原事实、条件与确定程度，不为了顺口编造因果或前提。

## 一、清晰与易懂

让读者读一遍就能抓到“谁、在什么条件下、做了什么、导致什么结果”，无需反复回读。

| 常见问题 | 问题示例 | 改写方向与示例 |
| --- | --- | --- |
| 抽象名词堆叠 | 系统对异常请求进行了有效性校验和拦截处理。 | 还原主语和动词：系统会检查异常请求是否有效，无效则直接拦截。 |
| 定语过长隔开主谓 | 在高并发且未开启本地缓存的旧版导出接口中出现的超时问题已经定位。 | 先交代条件或背景，再说主动作：旧版导出接口在高并发且未开启本地缓存时会超时，目前已定位这个问题。 |
| 术语悬空无锚点 | 本次改造引入了幂等键，服务端会据此识别同一笔提交的重试。 | 首次出现时顺手锚定作用：同一笔提交在重试时沿用同一个标识。服务端靠它识别重试，这个标识就叫幂等键。 |
| 句内信息超载 | 如果文件超过 50MB 且用户网络不稳定，除非提前分片上传，否则前端会在 30 秒后断开并清空已选队列。 | 仅在多层嵌套难抓主干时按“条件 -> 结果 -> 例外”拆开：文件超过 50MB 且网络不稳定时，前端会在 30 秒后断开并清空队列，提前开启分片上传可以避免这一问题。 |
| 过度压缩的伪精简 | 可如果两套搭配在输入上确实无从区分，单看横移的两个高概率档和转腕的两个高概率档，仍然无法读出哪个该配哪个。 | 补出具体对象、拆开动作与决策卡点：可如果在同样的画面和指令下，“向左移配顺时针转腕”和“向右移配逆时针转腕”这两套做法本来都合理，而又把横移和转腕拆开统计、只分别给出横移概率最高的两档（向左、向右）和转腕概率最高的两档（顺时针、逆时针），那么就算机器人先选定了向左移，单看转腕那两档概率，依然看不出该配顺时针还是逆时针。 |

## 二、易读与句式节奏（破除短句堆砌）

易读不是把所有句子都砍成十几个字的短句。连续堆叠结构相似的短句（“一个句子 + 一个句子 + 一个句子”），反而会打断阅读气流，让人觉得像电报或流水账。

### 1. 识别并消除“短句堆砌”

- **同一主语的连续动作，合并并省去重复主语**
  - 堆砌：工具支持批量导出。工具可以保存常用设置。工具还会保留文件的原始日期。
  - 融合：工具支持批量导出，既可以保存常用设置，也会保留文件的原始日期。

- **紧密相连的因果、条件或补充，用逗号和复句一气呵成**
  - 堆砌：我们正在排查导出失败的问题。问题可能与缓存有关。目前原因尚未确认。我们暂时关闭了自动重试。
  - 融合：我们正在排查导出失败的问题，目前怀疑与缓存有关但尚未确认，期间已暂时关闭自动重试。

- **区分主次，让句式长短错落**
  把背景、条件或过渡轻带在从句里，把核心变化或判断落在主句；长句展开解释后，可用一个短句收束重点，不要整段都是等长单句。
  - 堆砌：夜间备份在两点启动。它占用了大量磁盘带宽。同一时间报表任务也在运行。两个任务互相争抢资源。报表导出因此延迟了二十分钟。
  - 错落：两点启动的夜间备份占用了大量磁盘带宽，正好与同时运行的报表任务争抢资源，导致报表导出延迟了二十分钟。

### 2. 合并与拆分的边界

- **优先合并**：两三句围绕同一对象或同一事件推进，合起来主干依然一眼可见，且中间没有主题跳跃。
- **应该拆分**：一句话里塞进了两层以上条件、例外或括号说明，读者必须回头重看才能分清主谓；或者属于严格模式的操作步骤（一句一个动作，避免漏步骤）。

### 3. 段落与视觉结构

- **一段一中心**：一段只讲清一个问题、阶段或观点。如果同一段先讲故障现象、又讲排查历史、最后讲下季度规划，就按主题拆段。
- **结构服从关系**：时间顺序或操作步骤用编号；真正并列的要点用列表；包含因果与权衡的解释用连贯段落。不要把三句连贯因果硬拆成三个单句列表。

## 三、前后句逻辑（句间衔接）

当每句话单看没毛病、连起来却卡顿时，按下面四项逐一排查：

1. **旧信息接新信息（主位推进）**
   后一句开头优先接住前一句刚落下的对象或状态，再引出新信息，减少主语频繁跳切。
   - 断线：导出任务失败了。日志系统记录了磁盘写满。运维人员随后清理了临时文件。
   - 顺接：导出任务失败了，日志里有一条磁盘已满的记录。运维人员随后清理了临时文件。单凭这条记录，还无法确定导出失败的原因。

2. **消除指代歧义**
   先看上下文能否确定动作由谁执行。能确定就写出名字。若主体会影响读者的判断，而材料又没交代，就点明缺少哪条信息。
   - 歧义：服务 A 调用服务 B 超时后，它会自动降级。
   - 仅凭这句可以写成“服务 A 调用 B 超时后，会触发自动降级。原文没有交代哪个服务降级”。
   - 若上下文另有一句“这条降级策略由调用方 A 执行”，就可以写成“服务 A 调用 B 超时后，A 会自动降级”。

3. **连接词匹配真实关系**
   检查“因为/所以、但是/不过、如果/只要、而且/同时”是否符合真实语义。没有转折就去掉“但是”；没有必然推导就不用“因此”。
   - 错配：这个接口支持批量查询，但是响应字段和单条查询保持一致。
   - 修正：这个接口支持批量查询，且响应字段与单条查询保持一致。

4. **缺桥补桥，不靠连接词硬贴**
   把材料已经交代、但读者还没串起来的中间步骤写出来。机制只是推测时，点明假设。
   - 给定材料：缓存过期时间缩短到 5 分钟后，数据库的 CPU 使用率升高了。
   - 润色时保留先后顺序即可。若读者追问原因，可以解释一种可能：如果原本能命中缓存的请求在缩短有效期后需要查库，这些额外查询可能推高 CPU 使用率。判断这次是否如此，还要看缓存命中和数据库查询记录。

## 四、前后段逻辑（段间推进）

单段通顺但整篇散乱，多半是段间缺少推进主线或存在重复段。

- **按需要过渡**。如果前段给出一个现象，后段解释它为什么发生，可以从这个现象接着讲。若小标题已经点明问题，正文就直接展开。段落讲清了动作或结果，可以停在这里。
- **用语义过渡，删机械套话**：去掉“综上所述”“接下来我们再来看”“值得一提的是”“需要指出的是”等空洞过渡。
  - 套话过渡：……请求集中涌入，导致超时率上升。接下来我们来看解决方案。我们计划引入队列削峰。
  - 语义过渡：……请求集中涌入，导致超时率上升。为缓解这段时间的压力，我们计划引入队列削峰。

## 五、上下文逻辑（全文与跨轮一致）

在多段文档、长回答或多轮修改中，定稿前做一次全局一致性复核：

1. **口径与确定性一致**：前文标明“初步推测”“仅在测试环境复现”“约 60%”，后文和结尾总结不能悄悄升级为“已证实”“线上普遍存在”“大幅提升”。
2. **前提与范围一致**：前文限定“仅针对免费版用户”或“仅在开启异步模式时生效”，后文的建议和影响评估必须落在同一范围内；若范围扩大，明确写出条件变化。
3. **承诺与兑现一致**：开头说“主要有三点原因”或“分两步处理”，下文必须按相同数量和顺序逐一展开，不能漏项或中途换顺序。
4. **受众与视角一致**：整篇文本保持同一读者预期。若面向非技术读者，后段出现配置项或术语时同样需要解释；若面向工程师，前段不必铺垫常识。
5. **局部修改查接缝**：在多轮编辑中只改中间某段时，回读它上一段的结尾和下一段的开头，确认三处对齐：主语和指代没断、术语没漂移、前后结论不打架。

## 快速自检清单

定稿前用六问快速复核：

1. 随便抽一句，能一遍读出“谁在什么条件下做了什么”吗？有没有为了追求精简，把关键的中间动作或具体对象压成了抽象代称，逼着读者自己反向解压？
2. 朗读一遍，有没有连续三四句节奏雷同的“短句堆砌”或电报体？能自然合句的地方合顺了吗？
3. 任意相邻两句之间，读者需要自己脑补前提或猜“它/这”指谁吗？
4. 把每段压缩成一句话，拼在一起是一条顺畅的推理链，还是东一榔头西一棒子？
5. 开头设定的前提、范围、数量和确定程度，到了结尾还完全一致吗？
6. 这次改写有没有删掉原条件、改弱或改强原结论，或引入未核实的细节？
